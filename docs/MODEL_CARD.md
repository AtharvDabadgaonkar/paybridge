# Model Card — FraudLens

Regenerate every figure in this card with `python scripts/train_model.py` and
`python scripts/report.py`.

---

## 1. Model details

| Field | Value |
| --- | --- |
| Name | FraudLens combined fraud engine |
| Layers | A: 14 deterministic rules · B: supervised classifier · C: SHAP explanations |
| Selected model | **Random Forest** (300 trees, max depth 12, min leaf 15, balanced subsample weights) |
| Candidates compared | Logistic Regression, Random Forest, HistGradientBoosting |
| Selection criterion | Highest PR-AUC on the chronological **validation** split |
| Decision threshold | **0.759**, tuned on validation by maximising F1 |
| Secondary operating point | Highest recall within a 4% review budget, also solved on validation |
| Framework | scikit-learn 1.5.2 |
| Owner | Independent portfolio project |

## 2. Intended use

**In scope.** Ranking simulated payouts for analyst review inside PayBridge; demonstrating an
explainable detection architecture; comparing detection approaches at matched operating points.

**Out of scope.** Any real payment decision. Any production deployment. Any use on real customer
data. The model is trained on synthetic data from a known generative process and has no validated
relationship to real fraud.

## 3. Data

| Field | Value |
| --- | --- |
| Source | Synthetic, generated by `paybridge.data.generator`, seed 42 |
| Window | 90 days ending 2026-11-01 |
| Rows | 24,961 payouts across 200 fictional businesses, 8 corridors, 3 rails |
| Positive rate | 1.534% (target 1.5%, reached by bisection on the latent intercept) |
| Train / validation / test | 14,976 / 4,992 / 4,993 — strictly chronological |
| Test positives | **50 labelled fraud cases** |

Labels are sampled from a latent logistic model over observable risk factors: new beneficiary,
beneficiary age with large amounts, 24-hour velocity, young account, amount deviation from the
customer's own 30-day mean, off-hours initiation, corridor risk, recent failures, sub-threshold
clustering and recently changed payout details, plus Gaussian noise. A small share of businesses
receive an account-takeover style episode that elevates those same observable factors.

## 4. Features

20 features, every one observable at the moment of payment:

`amount_usd`, `log_amount`, `account_age_days`, `beneficiary_age_days`, `transaction_velocity`,
`days_since_last_txn`, `business_txn_count_30d`, `business_avg_amount_30d`,
`amount_vs_business_mean_ratio`, `recent_failed_count`, `hour_of_day`, `day_of_week`, `is_weekend`,
`is_round_amount`, `account_details_changed_days`, `corridor_risk`, `is_new_beneficiary`,
`payment_rail`, `corridor`, `currency`.

**Leakage controls (enforced in code).** `EXCLUDED_COLUMNS` blocks the label, post-outcome fields
(`transaction_status`, `settlement_time`, `compliance_status`), the rules baseline (`risk_score`,
`rules_*`), identifiers and the pricing outputs that are deterministic functions of rail, corridor
and amount. `assert_no_leakage()` raises if any of them reach the feature matrix, splits are
chronological, behavioural features are computed sequentially from prior events only, and a test
asserts the feature set and the excluded set are disjoint. The rules score is deliberately kept out
of the model so the two layers remain independently comparable.

## 5. Evaluation — held-out chronological test split (4,993 rows, 50 fraud cases)

**Candidate comparison** (selected on validation PR-AUC):

| Model | Val PR-AUC | Test precision | Test recall | Test F1 | Test PR-AUC | Test FPR |
| --- | --- | --- | --- | --- | --- | --- |
| Logistic regression | 0.192 | 0.242 | 0.440 | 0.312 | 0.340 | 1.40% |
| **Random forest (selected)** | **0.244** | **0.455** | **0.400** | **0.426** | **0.341** | **0.49%** |
| HistGradientBoosting | 0.202 | 0.288 | 0.420 | 0.341 | 0.171 | 1.05% |

**Approach comparison at each system's own operating point:**

| Approach | Threshold | Precision | Recall | F1 | PR-AUC | FPR | Alerts | Review volume |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Rules baseline | 0.400 | 0.184 | 0.520 | 0.272 | 0.281 | 2.33% | 141 | 2.82% |
| ML only | 0.759 | 0.455 | 0.400 | 0.426 | 0.341 | 0.49% | 44 | 0.88% |
| Rules + ML (combined) | 0.759 | 0.344 | 0.420 | 0.378 | **0.360** | 0.81% | 61 | 1.22% |

**At a matched operating point** (every system moved to recall 0.520, the rules baseline's recall):

| Approach | Threshold | False positives | Change vs baseline |
| --- | --- | --- | --- |
| Rules baseline | 0.400 | 115 | — |
| ML only | 0.476 | 98 | **−14.8%** |
| Rules + ML combined | 0.419 | 91 | **−20.9%** |

The combined engine removes about a fifth of the baseline's false positives while catching the same
fraud. This is the calculated result on synthetic data and is reported whatever its sign; the
evaluation page recomputes it live, including when it is unfavourable.

For reference, the Bayes-optimal ranking (the latent probability that generated the labels) reaches
PR-AUC 0.43 on the same split, so the model captures roughly 80% of the achievable ranking signal in
this simulation.

## 6. Explainability

- **Primary:** SHAP TreeExplainer on the selected forest; per-transaction contributions and a
  portfolio-level mean-|SHAP| view.
- **Fallback:** when SHAP is unavailable, a deterministic attribution (feature deviation from the
  training population × model importance). It is labelled `deterministic_fallback` everywhere it is
  shown and is never presented as SHAP.
- **Rules:** every triggered rule exposes its weight, its plain-language rationale and a recommended
  investigation question, so the rules portion of a score is self-explaining.

Top global drivers on the current model: `beneficiary_age_days`, `is_new_beneficiary`, `amount_usd`,
`log_amount`, `transaction_velocity`, `amount_vs_business_mean_ratio`.

## 7. Decision policy

```
combined_score = 0.60 × model probability + 0.40 × rules score
flagged        = model probability ≥ 0.759  OR  rules score ≥ 0.55
```

Band thresholds: low < 0.25 ≤ medium < 0.55 ≤ high < 0.80 ≤ critical. Every high and critical
outcome requires a human decision; the engine never auto-approves one, and no non-human actor can
record an investigation decision (enforced in `investigations.record_decision`).

## 8. Limitations

- **Synthetic data.** Labels come from a known generative process whose drivers are the same factors
  the detector observes. Real fraud is noisier, adversarial and non-stationary. **Treat these metrics
  as an optimistic upper bound, not a forecast.**
- **Small positive class.** 50 fraud cases in the test window; a handful of cases moves precision and
  recall materially. Confidence intervals are wide and are not reported as if they were tight.
- **No drift or adaptation.** No concept drift, no feedback loop between detection and fraudster
  behaviour.
- **Perfect labels.** Real labels are delayed, noisy and sometimes wrong.
- **Corridor slices are thin.** Per-corridor precision and recall on a few fraud cases are
  directional only.
- **Economics are assumptions.** Loss-given-fraud and review cost are modelling inputs, exposed as
  sliders rather than buried.
- **Recall misses the shadow-phase target.** Measured recall (~0.44–0.47 depending on the replay
  window) is below the 0.60 acceptance threshold. This is reported as a blocking gate, not waived.
- **No fairness analysis.** The synthetic entities have no protected attributes, so no meaningful
  bias assessment is possible here. On real data this would be a prerequisite, not an option.

## 9. Ethical and operational considerations

Fraud scores affect whether a business gets paid. The design therefore keeps a human in the loop for
every consequential outcome, makes every score decomposable into named rules and measured feature
contributions, writes an audit record for every decision, and keeps the model out of any automated
hold/release path. Before any real-world use: shadow mode on live traffic, independent model
validation, fairness assessment on real population data, and a monitoring and retraining plan.
